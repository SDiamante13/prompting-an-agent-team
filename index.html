      How I use the agent teams

      One real moment from the Orchestrator session. The whole approach is on a single screen: agents flag things, sessions pass messages, the lead brings a decision, and the human answers in one line.

      1. Sessions talk to each other. "sent to Doc-writer, another Claude session on this machine". The Orchestrator confirms it got a relayed bug report from the watcher session.
      2. A bug found by a different session. "DESIGNER, through Doc-writer, found a real bug". The designer found it while taking screenshots, the watcher passed it on, and the lead took it in. None of these sessions share a context.
      3. Options, not a fix. "What I've done: told verifier to keep the demo prompts short … It won't fix anything." Then four options, marked "not mutually exclusive". The agent does the thinking and the human keeps the decision.
      4. A recommendation. "a small slice 1b with options 2 and 3 (test first, then refactor, then a demo)". Even the fix is written as a thin slice with the team's usual loop.
      5. Steven's answer. "go with slice 1b, I'll switch models". He takes the recommendation and does the one part that's his: the model setting in .env, which agents are told never to touch.
      6. Watch the teammates. "View teammates: tmux -L claude-swarm-13969 a". Every agent runs in its own tmux pane that you can attach to and watch.
      7. The status line. Model, context used (14%), cost so far ($4.23), and permission mode. Checking cost and context is part of steering.
      8. The live team. main (the lead), committer (up 14 min, long-lived), verifier (up 5 min). pathfinder, builder and sweeper have already been shut down, so only the agents that are working show up.

      The techniques

      Written the way EventStorming writes policies: whenever this happens, do that. Depth 1 is the gist. Depth 2 shows the exact words and what the agent did. Depth 3 explains why it works and gives you a template to reuse.

      Whenever a new session starts, point it at the handoff file

      Handoff file as shared memory

      Planning happened in another tool and session. A single SESSION-HANDOFF.md carries the decisions over, so the new session starts from the plan instead of from scratch.

      Open for the promptDepth 2

      What Steven said

      Orient yourself @outputs/SESSION-HANDOFF.md.
      The Orchestrator read the handoff, checked the folders it named, and found problems on its own: the project wasn't a git repo, .env lived in the old Codex workspace, and both OpenRouter values were still empty.
      Depth 3: why it works
      • The handoff has a "latest decisions override earlier drafts" section. That stops the new agent from reopening questions the old session had already settled.
      • It ends with a ready-made "next-session starting prompt" and a "working preferences" block. The previous session wrote the next session's prompt.
      • @file puts the file straight into context, so the agent doesn't have to go looking for it.
      • Same move, smaller scale: after /compact at the slice 1 boundary, Steven's next prompt was "@outputs/agent-team.md continue with slice 1b". Compact, then point at the file.
      • The handoff also lists open choices and when each one has to be settled. That gave the agent its first questions.

      Reusable template

      End every session with: "Write SESSION-HANDOFF.md with: read-this-first, decisions that override earlier drafts, build order, open choices and when they're needed, artifacts, next-session starting prompt, working preferences." Start the next one with: "Orient yourself @SESSION-HANDOFF.md."
      Whenever work spans many steps, name the main agent the orchestrator

      Give the agent a role, then let it build the team

      Steven didn't design the team. He asked the orchestrator to propose agents with names, roles and responsibilities, and kept the right to approve, cut or add.

      Open for the promptDepth 2

      What Steven said

      You are the orchestrator, spin up an Agent Teams. And plan, code, and verify the thin slices. […] It's important to decide the members of the agent team, add more as necessary, but propose to me some agents (names, roles, responsibilities, etc)
      It proposed eight agents: navigator (itself), pathfinder, builder, sweeper, verifier, domain-steward, deployer and sensor-installer. Only four are active at the start, and the rest join when their slice comes up. They take turns on one working tree, so the builder and sweeper never edit at the same time.
      Depth 3: why it works
      • Propose, then approve. The agent does the design work. The human decides. That's cheaper than writing the roster yourself, and safer than letting the agent just go.
      • "Add more as necessary" lets the team grow. The orchestrator used this to bring agents in only when their slice starts, which keeps context and cost down early on.
      • The agent added a guard nobody asked for: the pathfinder checks that "we're not over-applying DDD (no invented aggregates)". That came from the handoff's "apply DDD proportionally" preference.
      Watch for: role names that sound good but overlap. Ask "which two agents could edit the same file at once?" The orchestrator answered it up front by running agents one after another.
      Whenever a slice is built, run the same loop: test, code, commit, refactor, commit

      Write your engineering discipline into the prompt

      The prompt gives the order of work, not just the goal. TDD, a commit, a sweep refactor in ACN micro-commits, another commit. The agent's habits become your habits.

      Open for the promptDepth 2

      What Steven said

      Use sweep refactors after intial implementation commit. i.e. test, code, commit, refactor (ACN), commit
      The loop became the team structure. The builder uses the tdd skill and makes the feat commit. The sweeper uses the sweep skill and makes "small ACN commits with tests green throughout". The verifier checks with the real app and mutation-tests the key tests.
      Depth 3: why it works
      • Skills are named, not described. "sweep" and "ACN" point to skills Steven already wrote (sweep, tdd, mutation-testing). Six words in the prompt bring in pages of discipline.
      • Two commits per slice. The behaviour change and the structure change land separately, which is Kent Beck's "make the change easy, then make the easy change" in the other order. Reviewers can read each on its own.
      • Seen in slice 2: builder first made an r commit (1ae878c, "the Coach now takes a Conversation", no behavior change), and only then wrote the failing tests for memory. That's Steven's CLAUDE.md rule, "Make the change easy, then make the easy change", applied by an agent without being told.
      • ACN (Arlo's Commit Notation) marks each commit with how risky it is, so an agent's refactor commits are easy to trust or check.

      Reusable template

      For each slice: failing test → minimum code → commit (feat) → run /sweep → refactor in ACN micro-commits, tests green after each → commit.
      Whenever a slice ends, ask: where are we, where next, why, and does it move us toward the goal?

      A built-in retro after every slice

      Four questions make the agent check its work against the goal each time, so it can't just keep shipping features.

      Open for the promptDepth 2

      What Steven said

      where are we now, where are we going next, and why and does that push up closer to our goals (first time ask about goals.
      The orchestrator made this report its own job ("write a where are we now / next / why / closer to goals? report after each slice") and, as told, asked about goals before starting: "What does success look like for you? … Is there a deadline or demo date? This is what I'll measure 'does it move us closer?' against."
      Depth 3: why it works
      • "First time ask about goals" is lazy goal-setting. Steven didn't write the goals out. He told the agent to ask for them once. The agent then worked out what it needed: success criteria and a date.
      • "Does that push us closer?" needs something to measure against, and the goals question provides it. Without goals, the report would just be a changelog.
      • It's a sprint review and a retro, cut down to four questions.
      • What it produced at the slice 1 stop:
        Where we are: Slice 1 is done: 38 tests, 20 commits, and the full loop ran once.
        Where next, and why: Slice 1b (recommended): cap reply length, a clear timeout message, fix Retry while busy … the timeout would show up again when we host at 2a.
        Does this move us toward the goals? Learning: yes. Fun: not yet. It's a bare connection test, and bugs 1–3 would hurt it. Solving real DDD problems: not yet. That starts in slice 3.
        Your call: approve slice 1? 1b or slice 2? faster model? fix your sweep skill?
        The "not yet" answers are the point. An honest check against the goals includes the goals this slice doesn't serve.
      • The answer Steven gave: "maximize learning and be a fun product to teach people DDD and help them solve specific DDD issues." The Orchestrator saved this to project memory as the measure for each slice: does it help learning, fun, or solving real DDD problems?
      Whenever a slice is done, stop and show a demo

      A human checkpoint, with evidence

      The agents can't chain slices on their own. Each slice ends with something Steven can watch, and the next one starts only when he approves.

      Open for the promptDepth 2

      What Steven said

      I want you and subagents to stop at every slice and show me a demo.
      The loop gained a hard stop: "verifier checks and records the demo → stop: demo + where we are, where next, why, how it moves us toward the goals → you approve." Demos go to outputs/demos/slice-NN.mp4, .gif and a slice-NN.md with the steps.
      Depth 3: why it works
      • "Tests pass" is the agent's claim. A demo is evidence. Asking for a demo moves the question from "did you say it works?" to "can I see it work?"
      • "You and subagents" matters. Without it, a subagent could take several steps before the orchestrator gets a chance to stop.
      • Ask for the evidence by name. 16 minutes in, Steven asked "where's the video demo?" The Orchestrator showed where things stood (builder is still on the setup commit, the video comes after sweeper), explained why there was no video yet, and offered a trade-off: record Part A before the refactor to get a demo sooner. A short question like this gets a status report plus options, not an excuse.
      • The gate loosened as trust grew. By slice 2, Steven wrote "continue on with the next slice if we've committed and pushed". That's a conditional go-ahead given in advance. The Orchestrator kept the demo but stopped blocking on it: "once the slice 2 demo is committed and pushed, I'll show it to you and go straight into 2a", with 2a's planning already running during the recording. The demo is still shown; it just doesn't hold up the next slice anymore.
      • Third stage: the gate became a notification. "/loop keep working on issues … Get my attention somehow to watch demo videos". The Orchestrator used PushNotification: "DDD Coach slice 2 demo ready: outputs/demos/slice-02.mp4 (2 min, memory across turns)." It also rewrote its "demo every slice" memory to match. The gate went from stop and wait (slice 1), to show it, but keep going (slice 2), to ping the human and keep pulling issues. The demo is still the evidence. Only how much it blocks has changed.
      • Stopping at every slice fits thin slicing. The slices are small, so the stops are frequent but short.
      Whenever you're unsure it's possible, ask the agent to find out how hard it is

      Ask for a spike, with your guess attached

      "Let's explore how complicated that is (ffmpeg right?)". Steven gives a guess and asks for a measurement, not a commitment. The agent ran a spike and came back with real numbers and a limit it had found.

      Open for the promptDepth 2

      What Steven said

      If you can take the video yourself let's explore how complicated that is (ffmeg right?)
      It ran four commands to test the idea: agent-browser record to WebM, ffmpeg to MP4 and GIF, and a toggleable .srt caption track. It also found a limit: this ffmpeg build has no drawtext filter. The fix was to inject caption banners into the page while recording. Cost estimate: about 30–60s per slice.
      Later, at team scale (18:35 UTC): Steven asked PRODUCT OWNER to find "quick spikes … that a subagent of the Orchestrator can take up async" (PO Prompt 5). PO filed the questions as issues, and the Orchestrator sent out three spikes in 13 seconds, each answering one GitHub issue that blocks a feature. spike-79: does Netlify streaming get past the ~30 s cutoff? It proves this with a throwaway function that streams for 60 s and calls no model (this gates #8 streaming). spike-80: the DDD Reference's token count, license and attribution (this gates the #58 knowledge base). spike-81: OpenRouter spend caps, alerts, and whether a spent key returns 402 or 403, "with a doc citation" (this gates #72). All three are "No product code, no commits." The issue body is the question, and the spike's answer decides the slice. It paid off within 4 minutes: spike-81 found that OpenRouter also returns a transient 402 (openrouter_in_flight_budget, with Retry-After), which is likely when a whole room uses the app at once. But the #75 code mapped every 402 to "out of credit". PO filed #83 as P0 at 18:39: "today it would tell the room the coach is out of credit". A fix builder in its own worktree started 40 seconds later. (Once Steven dropped conference priority at 18:40, #83 was folded into the next normal deploy.) spike-79 overturned the docs: "Function streaming does not get past ~30 s." A stream that sends a chunk every 2 s is still cut at ~30.3–31.0 s, and "the cut is silent": HTTP 200 and a clean close, so only a missing final event shows it happened. The docs say 60 s. Twenty minutes later, the #8 streaming plan was briefed with that spike's closing comment on its reading list.
      Depth 3: why it works
      • "Explore how complicated" asks for information, not a feature. The agent tried it with a throwaway example.com recording and didn't touch the project.
      • "(ffmpeg right?)" gives the agent a starting point without locking it in. It confirmed ffmpeg, then added agent-browser's own recorder and a workaround for the missing filter.
      • The answer came back as a working pipeline plus a cost estimate, which made "yes, do it" an easy call.
      Friction found: ffmpeg without drawtext or subtitles can't burn in captions. Captions drawn in the page get around it.

      Named sessions and a watcher

      The build session is named "Orchestrator". A second session (the one that wrote this page) reads its transcript on a loop and takes notes, so the builder never has to stop to document.

      Open for the promptDepth 2

      What Steven said (to the watcher)

      listen to another Claude session called Orchestrator. And I want you to make a note of […] how did I prompt the AI and what techniques did I use. […] just keep watching the orchestrator session to keep taking notes so just keep checking /loop
      The watcher found the Orchestrator through the session list, reads its .jsonl transcript on each tick, adds new prompts to this page, and copies each slice's demo screenshots here.
      Depth 3: why it works
      • Keeping the jobs apart means the builder's context isn't filled with documentation, and the notes don't depend on the builder remembering to write them.
      • /loop with no interval lets the watcher decide how often to check. It checks more often while slices are running and less often while the Orchestrator waits for Steven.

      Write it down first, make it real later

      The team roster goes into a markdown note first. Steven will turn them into real Claude Code agents (.claude/agents/*.md) once the team has proven itself on a slice or two.

      Open for the promptDepth 2

      What Steven said

      okay make note of the agent archtypes and we can add them as agents in the Claude Code sense.
      It wrote outputs/agent-team.md with the roles, the slice loop and the demo recording recipe, and said plainly: "Nothing is installed in .claude/agents/ yet. Just say 'install agents' when you want that."

      • "Archetype" is the right word. They're roles, not code yet. A note is cheap to change. An installed agent definition turns into structure people rely on.

      Whenever a routine has rules, give it a one-word command

      Skills as verbs

      "commit" at the end of a prompt triggers Steven's commit skill: review the diff, block secrets, write a single-sentence message, flag anything odd with ❗️.

      Open for the promptDepth 2

      What Steven said

      Let's begin with git setup. commit
      It ran git init, copied .env.example and .gitignore, grepped the staged files for .env, secrets and keys, and committed edc716d. It answered with "☀️✅ ♻️ Committer rules re-read" and raised one ❗️: the handoff still points at the old Codex path.
      Depth 3: why it works
      • Emoji markers show which rules are loaded. ☀️ means the global CLAUDE.md was read. ✅ means the commit skill is active. ♻️ means the agent re-read the skill after committing. You can check the agent's state at a glance.
      • The ❗️ flag is built into the skill: the agent must raise problems and ask instead of fixing them quietly. That's how the stale handoff path came up.
      • The agent also saved "demo every slice" to project memory on its own, so the rule survives /clear.

      Reusable template (from the commit skill)

      Add ✅ to STARTER_SYMBOL. `c` means commit. Don't write any code. Stage all files that are not secrets. Succinct single-sentence messages. If you spot issues, flag with ❗️ and ask whether to proceed. ALWAYS re-read this skill after every commit and say "♻️ Committer rules re-read".
      Whenever the future is uncertain, ask "what if" instead of making it a requirement

      Keep the option, not the feature

      "Simple now, but what if we want React3D?" Steven doesn't ask for 3D. He asks the agent to keep the path to 3D cheap. The agent switched its own stack choice to fit.

      Open for the promptDepth 2

      What Steven said

      2. great, 3JS and crazy UI with GSAP might be super awesome at some point so let's built it initially to be simple, but what if we wanna to do React3D
      It dropped its own recommendation (vanilla TS) and chose Vite + React + TS, because React Three Fiber needs React. It also added a guard: "domain logic will be plain TypeScript with no React in it. React only renders it." 3D and GSAP libraries come in only when a slice needs them.
      Depth 3: why it works
      • YAGNI with an escape hatch. "Simple now" rules out building early. "What if" makes the agent think about how much a change would cost later. Together you get a cheap architecture decision without any speculative code.
      • The agent's answer is textbook DDD: keep the domain core independent of the UI, so the UI can change (2D log → 3D board) without touching the model.
      • Saying "great" to the recommendation and then asking "what if" gives the agent room to change its own mind instead of arguing for its first answer.

      Reusable template

      Build it simple for now. What if we later want <big future thing>? Pick the option that keeps that cheap without building any of it yet.

      How the orchestrator prompts its own agents

      Steven's short prompts became a detailed brief for the pathfinder agent: a role, what to read first, what's already decided, a tight scope, a numbered return format and a word limit. How the human prompts shapes how the agents prompt each other.

      Open for the promptDepth 2

      What Steven said (spread across 4 prompts)

      You are the orchestrator … plan, code, and verify the thin slices … test, code, commit, refactor (ACN) … goals are to maximize learning … let's built it initially to be simple
      The Orchestrator's brief to pathfinder is structured like this:
      • Role and limits: "You are pathfinder, the read-only slice planner" … "Don't write files."
      • Read first: five named files, plus "grep for the slice IDs; don't dump the whole file".
      • Decided: stack, env handling, goals and workflow, so nothing gets reopened.
      • Scope: "slice 1 only … Do NOT plan slice 2 beyond noting the seam it will need."
      • Check, don't recall: "Research the actual current @openrouter/sdk API".
      • Return format: 7 numbered sections, "under ~900 words".
      Depth 3: the full brief, and why it works
      • "Decided:" is the handoff pattern again, one level down. Each subagent gets a small handoff so it can't reopen settled questions.
      • "Do NOT plan slice 2 beyond noting the seam" is thin slicing written as an instruction. It keeps the future in view without building for it (see keep the option).
      • Proportional DDD: "value objects only where they earn their place … No invented aggregates or services". This carries the handoff's "don't over-apply DDD" rule down into the plan.
      • The payoff for checking instead of recalling: pathfinder came back with "⚠️ The README is out of date. It shows a flat chat.send({messages, model}), but the 1.3.27 types wrap the request: chat.send({ chatRequest: {…} })". It checked the .d.ts files on unpkg. A plan written from memory would have given the builder the wrong API.
      • Demo script requested at planning time, including "how to force a failure deterministically … without a real key". The demo gate is designed in before any code is written.

      Builder's brief: role boundaries and inherited rules

      • Each role stays in its lane: "Do NOT do broad refactors. A separate sweeper agent does that" … "Do NOT start the dev server for demos; the verifier does that." … "Stop after commit B."
      • Steven's CLAUDE.md is passed down: "Keep methods ≤25 lines, use small pure functions and strong types, and don't add comments explaining changes." Subagents don't reliably pick up your global preferences on their own, so the orchestrator restates them.
      • The commit skill is passed down: "Each message is one short sentence. No Co-Authored-By or any Claude attribution lines."
      • Secrets are protected: "Never read, print or log the contents of .env" plus a mechanical check: grep -rl "OPENROUTER_API_KEY" dist before every commit.
      • Skills called by name: "Invoke the tdd skill … predict each failure before running, hardcode first, triangulate."
      • What one agent learns, the next is told: pathfinder's stale-README finding goes straight into the builder's brief.

      Sweeper's brief: passing on what builder saw, without trusting it

      • Smells are passed on, but must be checked: "The builder already spotted these smells. Verify them yourself and don't take them on trust." One agent's findings become the next agent's hypotheses, not its facts.
      • Behavior stays fixed: "focus stays on the disabled Send button … Do NOT fix it. List it in your report as a behavior candidate." It's the refactoring rule: structure changes and behavior changes don't mix.
      • The protocol overrides the skill: "Commit protocol (overrides the skill's own committing): you must NOT run git commit." A skill is reused, and the brief narrows it to fit the team.
      • Suggestions for the skill are part of the job: "any sweep skill improvement suggestions". This comes from Steven's CLAUDE.md ("After completing tasks that used skills, suggest improvements to those skills") and is passed down to every agent.

      Verifier's brief: the spike turned into a procedure

      • The ffmpeg spike from prompt 2 is now step-by-step instructions: inject a caption banner with agent-browser eval before each step, "pause about 1.5s after each visible change", convert "with ffmpeg (no drawtext filter available)". A limit found in the spike became a rule in the brief.
      • It checks, it doesn't fix: "Do not fix code." … "Report findings; don't fix them." Keeping the checker separate from the builder is what makes it independent.
      • Evidence for each criterion: "record pass or fail for each with evidence". The demo gate gets an acceptance table, not just a video.
      • Planned failures: network route "**/api/chat" --abort forces the error path without breaking the server.

      Slice 1b's pathfinder brief: what the team learned, now in the instructions

      • Findings became scope. All 5 items come from the verifier's and DESIGNER's slice 1 findings, in the same ranked order.
      • Other sessions' lessons reach the team. "the verifier records with agent-browser (--session verifier, reuse the dev server on :8888 …)". That's the browser-collision fix, which went from the watcher to DESIGNER to agent-team.md and now into a brief.
      • It looks ahead to the next risk: "Research Netlify's hosted sync-function timeout (the default may be 10s, not 30s; this matters for slice 2a)".
      • Demos are designed around slow steps: "Show the timeout message by some reproducible means that doesn't need a 30s wait".
      • The role changed on purpose: in slice 1 pathfinder was told "Don't write files". Now it writes outputs/slice-01b-plan.md itself, copying slice 1's plan format.

      Slice 2's sweeper brief: skill bugs patched in the brief

      • A skill bug found in slice 1, fixed here: "the sweep skill wrongly maps e to Extract, but e means environment, so don't use e for extracts". Slice 1's sweeper suggested the fix. Until Steven updates the skill, the brief overrides it.
      • A stopping rule against churn: "Stop when the remaining smells aren't worth it (aim for roughly 3–8 commits, not churn)". Slice 1's sweep made 16.
      • Bugs get reported, not fixed: "If you find a real bug, report it to team-lead and don't fix it." A refactorer that fixes bugs is changing behavior.

      model-scout's brief: a relayed request turned into a scoped job

      • The watcher's context ended up in the brief. The relay mentioned Priya's "paraphrase turned into a confident wrong conclusion", and the brief asks for "a trap prompt where a paraphrase invites a confident wrong conclusion". Synthetic research → watcher → lead → a test case, in about four minutes.
      • Spend is gated: "RESEARCH + PROPOSAL only. Make NO paid OpenRouter calls … the user approves spend first." Research that costs money needs a human decision, just like secrets.
      • Check, don't recall, again: prices come from the live catalog (curl …/api/v1/models), and whether reasoning tokens count toward the cap is checked "in node_modules .d.ts".
